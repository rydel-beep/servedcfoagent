## 2. CRITICAL Findings

### CRITICAL-1: Churned clients counted in MRR and client count

**Impact: MRR overstated by ~$7,800/mo, client count overstated by 4-5**

The persisted snapshot (`snapshot_state.json`, generated 2026-05-29) includes churned clients in `client_health.clients`:

| Client | Status in snapshot | Current MRR | Known churned? |
|---|---|---|---|
| Asian Streat | Active | $2,200 | YES — in KNOWN_CHURNED |
| 1st Edition Bar | Active | $2,550 | YES — in KNOWN_CHURNED |
| The Advocate | Active | $3,050 | YES — in KNOWN_CHURNED |
| Nonnas Pizzeria and Cucina | Active | $0 | YES — in KNOWN_CHURNED |
| V Noodle and Sushi bar | Active | $0 | YES — in KNOWN_CHURNED |
| Bunni Beez | Active | $0 | YES — in KNOWN_CHURNED |
| Riverloop Cafe | Active | $0 | YES — in KNOWN_CHURNED |

**Root cause:** The snapshot was generated by a version of `pull_client_health()` that added `_is_confirmed_churned()` filtering AFTER this snapshot was persisted. The code now correctly filters with `CONFIRMED_CHURNED_PREFIXES` — but the persisted snapshot is stale (3.9 days old) and predates the fix.

**Additionally:** The `active_clients` and `client_reconciliation` keys are **missing entirely** from the persisted snapshot. The code to derive them exists in `snapshot.py` but the persisted data was generated before that code was added.

**Fix:** Trigger a fresh refresh (`POST /cfo/refresh`). A new snapshot will include churned filtering and the derived client sections.

**Displayed numbers (from stale snapshot):**
- client_health.total_clients = **31** (includes 7 churned)
- client_health.current_mrr = **$58,601** (includes $7,800 from churned)
- **Clean estimates:** ~24 active clients, ~$50,801 MRR

### CRITICAL-2: Stripe data anomaly — 1 active sub but $57K MRR

The snapshot shows:
- `stripe.mrr` = $57,041
- `stripe.subscriptions.active` = **1**
- `stripe.subscriptions.cancelled` = 1
- `stripe.subscriptions.past_due` = 1
- `stripe.failed_charges_count` = **30**

**This is internally inconsistent.** $57K MRR cannot come from 1 active subscription. The Stripe MCP likely uses different methods for each metric — `get_stripe_mrr` may aggregate from invoice line items or a different calculation than `get_stripe_subscriptions` which may be counting differently.

**Impact:** The Stripe active_subs count is used as a proxy for customer_count. With `active=1`, the dashboard's Stripe Health panel shows "1 Active Sub" which is clearly wrong relative to the business reality.

**Needs investigation:** Compare Stripe MCP tool responses with actual Stripe dashboard data.

### CRITICAL-3: Xero and GHL not connected — 4/7 Hormozi metrics unavailable

The degraded list shows:
- `xero`: "XERO_CLIENT_ID or XERO_CLIENT_SECRET not set"
- `ghl_pipeline`: "GHL_SALES_API_KEY or GHL_SALES_LOCATION_ID not set"

**Impact:**
- **No Xero data** → profit is null, gross_margin is null, revenue is null, ad_spend is null
- LTGP:CAC = **unknown** (needs gross_margin_pct)
- Gross margin = **unknown**
- Op efficiency = **unknown**
- CAC is **understated** (ad_spend = $0 because Xero is missing)
- Waterfall panel shows "No Xero P&L data available"
- Net profit, COGS, OpEx — all missing

This means the dashboard currently shows **sales/funnel data and Stripe data only**. The financial picture is incomplete.

### CRITICAL-4: Cookie `Secure` flag is conditional

In `dashboard/routes.py:53`:
```python
secure=request.is_secure,
```
And in `dashboard/auth.py:50`:
```python
secure=request.is_secure,
```

On Railway (behind a proxy), `request.is_secure` may be `False` if the proxy terminates TLS. The cookie would then be sent over HTTP. Railway uses HTTPS externally but the app may see HTTP internally.

**Risk:** Medium. The token cookie may not have the `Secure` flag set, meaning it could theoretically be intercepted if there's a non-HTTPS path. Railway forces HTTPS externally so practical risk is low, but the flag should be `True` in production.
